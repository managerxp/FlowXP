# Languages (i18n)

English, Hindi (hi), Malayalam (ml), Tamil (ta), Bengali (bn), Telugu (te) and Kannada (kn) on the website, the web app and the phone app. English is the source and the fallback.
Language is **display text only**: it never changes currency, country, timezone, tax, rounding, stored amounts or any business setting.

## Which language shows

Signed in: the person's own saved choice > a choice made on this device before signing in (then saved for them) > the business default > the device's language > English.
Signed out: the choice made on this device > the device's language > English. While the session is being checked, or offline: what this device last showed.
Another person's remembered language on a shared device is never used. Rules live in `frontend/src/i18n/config.js` (`resolveLanguage`) and `mobile/src/lib/langrules.ts` (`resolveLang`); both are unit tested with the same cases.

| Where it is stored | What |
|---|---|
| `users.language` | the person's own choice (NULL = never chose); `PATCH /api/auth/language {language}`; returned by `GET /api/auth/me` as `user.language` |
| `businesses.default_language` | what staff see until they choose; `PATCH /api/businesses/current {default_language}` (owner); returned as `businesses[].default_language` |
| web `localStorage flowxp.lang` / phone kv `language` | `{lang, uid, pending, derived}`: so the app opens in the language with no network. `pending` = chosen but not yet saved on the account (offline), sent at the next start or sign-in. `derived` = just what was shown (business default / device), not a choice |

Supported codes are checked on the server (`backend/src/utils/locales.js`). Migration `0103_languages.js`.

## Web (React 19 + Vite)

`i18next` + `react-i18next`. English is bundled; each other language is a separate chunk loaded when chosen (`src/i18n/index.js`), and the build's precache list includes those chunks so an installed copy works offline. Resources: `frontend/src/i18n/locales/<code>/<namespace>.json`, namespaces `common nav auth site settings errors` (more are added as screens are converted: billing, pos, inventory, purchases, customers, kitchen, reports, subscriptions, notifications).
Components: `LanguageSync` (mounted in `main.jsx`, applies the rules), `LanguageSelect` (native select, each language written in itself, no flags; in the site header, the auth pages and the profile menu), the Language card in Settings > Business (own language, and the staff default). `<html lang>` and `dir` are set on every change. Switching needs no reload.
Use `const { t } = useTranslation('ns')` and `t('some.key')`; text with markup uses `<Trans>` (see `AuthPages.jsx`); plurals use `_one` / `_other` keys (`nav:shell.trialLeft`).

### Screen text: `useT` and `tr('English text')`

Most screens use a second, lighter form so 225 screens do not need hand-made keys: `const tr = useT();` and `tr('Save changes')` (`frontend/src/i18n/useT.js`; texts in `locales/<code>/screens.json`, the English text is the key, values go in `{{braces}}`). A text nobody translated shows in English. A label written once in a list is marked `T('Cash')` and shown with `tr(label)`.
`node scripts/i18n-extract.mjs [--write] [files or folders]` converts screens automatically (plain text, button/label/placeholder attributes, toasts, dialogs, error setters, text mixed with values, templates, option lists); what it cannot do safely (plurals, conditional words, text outside a component) is listed in `scripts/i18n-skipped.txt` for hand work. `node scripts/i18n-prune.mjs` drops texts no screen asks for. `npm test` checks every `tr()`/`T()` text is in `screens.json` and that every language has a real translation of it.
Converted so far (about 4,580 texts in 6 languages, core screens plus every industry: hotel, salon, gym, gaming, wholesale, distributor, spare parts, pharmacy): dashboard, billing and invoices, products, inventory, customers, orders, payments, reports, security, staff, business settings, outlets, activity log, purchases, returns, expenses, GST filing, notifications. Not yet: the admin console and the marketing pages' body text. Left for hand work: about 230 places (plurals, conditional words, text split around links) listed in `frontend/scripts/i18n-skipped.txt`, and short option words built from data (vehicle types, Fast/Slow/Dead).

## Phone (Expo)

The existing small system (`mobile/src/lib/i18n.ts`: `t('English text')`, English as the key, a dictionary per language) was kept, not replaced. Hindi covers 1206 texts; Malayalam, Tamil, Bengali, Telugu and Kannada (`i18n.more.ts`) cover a **core set of 105 texts** (tabs, signing in and out, creating an account, billing buttons, offline and error screens, report a problem, the first dashboard numbers); anything not translated shows in English. The device language comes from `Intl` (no extra package). `langpref.ts` keeps and sends the choice.

## Translation status

Hindi, Malayalam, Tamil, Bengali, Telugu and Kannada were **machine-generated and have not been reviewed by a native speaker**. `LANGUAGES[].status` in `config.js` says `machine`; change it to `reviewed` only when someone has signed it off. The app says so next to the picker. Get them reviewed before presenting them as professional translations.

## Adding a language (e.g. Urdu `ur`)

1. `backend/src/utils/locales.js` LOCALES, `frontend/src/i18n/config.js` LANGUAGES (Urdu / Arabic: `dir: 'rtl'`), `mobile/src/lib/i18n.ts` Lang and LANGS.
2. Web: copy `locales/en/*.json` to `locales/<code>/` and translate; the test checks every key, placeholder and plural form.
3. Phone: add a dictionary in `i18n.more.ts` and `DICTS`.
4. Right-to-left needs a layout pass (the app uses left/right Tailwind classes); `dir` is already switched, but do not offer `ur` until the screens have been checked in it.

## Tests

`cd frontend && npm test` (rules, every locale and namespace complete, same placeholders, every key the code uses exists in English, every sidebar label translated); `cd mobile && npm test`; `cd backend && npm test` (`language.test.js`). Live: `mobile/scripts/language-live.mts`.
